# Taichi GPU: Accelerated Fast Multipole Method

## Academic Context & Attribution
This repository was developed strictly for academic purposes as part of a university project. 

It builds directly upon the original **Taichi / ExaFMM** implementation by **Q. Zhu** ([original repository link here](https://github.com/QirongZhu/taichi_collisional)). The primary objective of this project is to extend the existing codebase by designing, porting, and optimizing CUDA-accelerated GPU kernels  to evaluate heterogeneous performance and parallel efficiency. 

All original algorithms, core architecture, and foundation code remain the intellectual property of Q. Zhu and the original authors.


## The algorithm
The algorithm implemented by Q. Zhu is a specific version of the **Fast Multipole Method (FMM) for the N-body problem**, and his paper can be found [here](https://arxiv.org/abs/2012.02207).
In brief, the FMM is a mathematical framework to approximate the problem. Bodies are partitioned recursively in clusters by 3D distance, until the cluster size is under a specified `ncrit` particles. An octree is constructed based on the partitioning. We call partitions Cells. Each Cell will have a set of parameters that approximate the physical properties of the bodies it refers to. These are computed traversing the octree bottom up. For each pair of cells, the physical interaction between them can be approximated if they are sufficiently well-separated. This approximation is called **Multipole to Local (M2L)**. If it can't be approximated, the interaction between each particle of the two cells has to be computed, as in the original N-body, considering  **Particle to Particle (P2P)** interactions between leaf cells. The effects of the approximation are then propagated to child cells and finally to bodies in a top-down pass. 
Notably, the original implementation uses a dual tree traversal. Instead of computing interactions once and writing forces to both cells (which would require atomic operations), each pair is evaluated twice: cell A acts as target and cell B as source in one pass, and vice versa in the other. This allows concurrent target updates without race conditions.

## The GPU acceleration
As of now, only the P2P interactions side of the algorithm has been taken care of. Future work will focus first on accelerating M2L interactions (these two are the heaviest part of the algorithm). The final aim is to have most of the work be done by the GPU. 
GPU code is written in CUDA C++. Changes and additions to the algorithm code is to be found in `src/cuda`. Every other C file was left untouched. Every test and profiling pass was performed on a NVIDIA GeForce RTX 4060 Laptop GPU. Initially, only the use of fp64 data type was considered, since dealing a physics problem. Later on, profiling using fp32 was also performed: since the algorithm is compute heavy, and the specific GPU has a quite reduced fp64 pipeline, the risk was having different bottlenecks hided by the one on fp64. 
The P2P interaction has actually 3 implementations. Each is used in a different phase of the integration. They were implemented in CUDA in the same kernel, with the use of templating. The effort of optimization was mainly onto the `standard` implementation, which, comprising multiple square root and division operations, was by far the heaviest.

### First porting
#### Host side
With P2P interactions being issued for each cell pair (each with 1-255 bodies, as ncrit was fixed at 256), this algorithm was not one of those with the data laid down for the GPU to work with it. The approach was having the interactions performed in the same GPU kernel launch, organising the metadata of each cell in a interaction matrix stored in CSR format. The `horizontalPass` (`traverse_eager.h`) was now perfomed twice. In the first pass, the number of P2P interactions for each cell as targets is noted. The matrix is then prepared and in the second pass the source cells indices and metadata are stored in the matrix. This metadata comprises the pointers to the first body of the cell in the `Bodies` array, which is a data structure apart. These two data structures are loaded into the GPU.

#### Device side
Following the previous consideration, the baseline was implemented with the simplest of the approaches: each block computes interactions for a single target cell, with each thread assigned to a single target body. In this way, the target data is loaded once, and the resulting forces (and more) were written once at the end. The block loops on the source cells -> source bodies, loading each time for each thread a source body from global memory to compute the interaction.

#### Profiling, Basic optimizations, Considerations
Profiling with Nsigth Compute showed first of all how much the FP64 pipeline was immediately saturated. Of course loading a source body at a time from the global memory introduced stalls. Moreover, it signalled workload imbalance. In this phase, the only immediate optimisation that worked was restructuring the math of the standard implementation, using intrinsics as Reciprocal Square root `rsqrt()` and the reciprocal `1/x` (which is compiled into `RCP`), and using their results as basic blocks. It indeed reduced the compute time by around 27%. Every other attempt to tackle what NCU was pointing out, was unsuccessful, even using shared memory to keep source bodies on the SM. It was in the end evident, that the heavy workload imbalance caused the unreliability of the NCU aggregated metrics. Indeed having cells of an incredibly variable size (average 68) and number of source cells too, there were blocks doing much more work than others, but also threads. Restructuring the work assignment was essential to move forward.

### Workload balance
#### Host side
The approach chosen for balancing was partitioning by number of body-to-body interactions. The aim had to be trying to have an equal number of these per thread. Assuming it would be possible distributing an equal amount of work to the threads inside a block (see next), obtaining a balanced distribution between blocks was the main challenge. The solution revolved around the idea of duplicating when needed a target cell in the interaction matrix, splitting the workload. First of all, the source cell list is divided, not by number of cells but by cumulative source bodies. If further reduction is needed, the target cell is split. This is an extreme case, as it would cause accessing the same exact sources by different blocks. A target workload per block is computed to properly split. It is computed based on the number of waves per streaming multiprocessors we want to achieve. Since some workloads will be even smaller, they would unbalance again. This is why the target cells with less body-to-body interactions are inserted in a different interaction matrix, and will be processed by a second, smaller, kernel launch.

#### Device side
Although the memory layout remained largely identical —only requiring atomic additions for targets split across multiple blocks— the execution model on the device was restructured. To avoid having threads assigned to unexisting target bodies, each active target body is assigned an entire warp. In this case of course many warps will be assigned to multiple targets. For each target assigned, each warp will span the source bodies, in a way which is not much different from the single thread before. This of course doesn't exclude cases where warps are assigned a different number of targets or source cell with a size that causes a lot of divergence, but is at least an improvement. This whole restructuring allowed indeed to cut again 27% of the kernel duration.

#### Shared memory
Loading all the many source bodies from global memory for each target body, was of course suboptimal. Even so, the FP64 utilisation caused the double precision version to be already compute bound. The single precision version, however, was bottlenecked by memory traffic in the L1/L2 cache (NCU generated roofline). Tiles of memory were then loaded to shared memory for each group of #warps-per-block targets. It caused indeed a negligible reduction for the double precision version, while  the single precision version took 4% less than before. In both cases the number of requests to global memory dropped by around 80% and the transferred memory from L2 to L1 by 70%.

#### Dead end
Unfortunately those numbers were not enough to make me realise that I didn't need to tackle memory accesses anymore. Not in that sense at least. I spent most of the remaining time trying to make a warp shuffle trick to have a single load to shared memory per source cell for a whole block, but in the end it increased the register pressure, and the reduced occupancy counterbalanced the gain. 
I only later came to the conclusion that, with Tex Throttle and Short Scoreboard stalls, the problem was not memory throughput but memory latency. Unfortunately, any later attempt I had time to try, didn't find the right trade-off between reduced stalls and occupancy.
